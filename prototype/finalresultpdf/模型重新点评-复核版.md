## 评前先立三条口径

1. **三条证据轴**：短任务（4 模块 16 criterion，A=无计划 / B=读 phi_3 计划）、长任务（2 项目 10 milestone，闭环）、Reviewer 调试重放（B11 修复，14 候选）。任何"综合排名"都是对这三轴的加权假设，所以本文不给总分，只给分场景结论。
2. **token 三种读法**：绝对总量（对账单）、单位成本（token/成果）、构成（input/output/cache）。三者会给出相反的结论——qwen 总量偏贵但单位成本全场前 5 名最低；B06 的 863K 里 96.1% 是 cache（input 仅 108），LongCat 的 provider 无 cache（838K input 全价）。**跨 provider 直接比总 token 是不公平的**，下文凡说贵/便宜都注明口径。
3. **gate 的读法**：严格榜的一票否决保留不动（协议纪律是真实能力），但 raw 完成度必须并列陈述，否则会把"违规"误读成"不会写代码"。本轮有三起典型：短 B12（.pytest_cache）、长任务 doubao-2.0-pro 与 mimo-v2.5（均 6/7 指令）。

另有三个测量学注意点，评单个模型时会引用：
- **luna 的长任务只有一次有效运行**（原始轮两次尝试均被 provider 403 拦截，`subtest_7-provider-failure.json` 有记录），6/10 无稳定性佐证；
- **glm-5.2 的 5/10 是 F3 定向反馈后的修订轮**（累计 4,332,044 token），不可回填为 pass-1 能力；
- **reviewer 榜的性能中位数**，subtest_2/subtest_10 只含单项 wide_50000（deep 超时），61.6/63.3 ms 与其他行的 deep+wide 口径不可比。

## 第一梯队：两种"最强"

### qwen3.8-max —— 长程推进力的孤例，且单位成本其实最低

数据面：长任务 8/10（第二名 6/10），coverage 0.85，是唯一摸到"接近做完一个项目"的候选（尽管全场 0/2 完整闭环）。短任务 A/B 双 16/16。Reviewer #3（7/8，cross_hashability 未过）。

我的重点与原点评不同：**qwen 的"贵"是个会计口径错觉**。短 B 863K 只是满分组第 5 高（B03 1.41M、B02 900K、B07 880K、B01 869K 都更贵），而它的 863K 里 96.1% 是 cache、input 仅 108——按 input+output 算实际推理量约 3.4 万 token，是满分组最低档。长任务按每严格 milestone 计 446,954，为严格榜前 5 名最低。**它不是"成本天花板"，是"产出密度最高"**。真正的短板是：七次自测零缺陷发现（验证冗余），以及短任务从不拿第一（能力稳但不追求单次效率）。

选它的理由只有一个，但足够硬：如果任务是"接手一个项目连续推进两天"，本轮数据里没有第二个候选及格。

### gpt-5.6-luna —— 无脚手架条件的全场最强，但要为"计划"交最重的税

数据面：短 A 第 1（306K，满分四家中 token 第二低）；Reviewer #1（官方 16/16 + 资源 2/2 + 补充 8/8，唯二全满分之一）；长任务 6/10 第 2。

luna 的画像非常一致：**给它越少的约束，它表现越好**。读 phi_3 计划后 raw 分毫未涨、token 从 306K 涨到 880K（+574K，全场最重计划税），排名从第 1 掉到第 7。它的防御性实现（异常安全等值比较、溢出回退 `math.inf`、10^9 分块大数）超出了本轮 criterion 的覆盖范围——这是"为看不见的边界买单"，在更严苛的评分集下会变现，在本轮只是成本。

两个保留意见：长任务 6/10 建立在唯一一次有效运行上（原始轮两次 403）；22 次请求的验证风格与 kimi 同病（零缺陷发现）。定位：无现成计划、要求高鲁棒性的自主任务首选；强流程（必须读计划/文档很厚）场景要预算翻倍。

## 第二梯队：两种"稳"

### kimi-for-coding —— 唯一三轴全前列，且差一步就是短 A 冠军

数据面：短 A #4（194K）、短 B #4（804K）、长任务 #3（5/10）、Reviewer #2（8/8，与 luna 并列唯二全满分）。

一个被原点评忽略的细节：**kimi 短 A 的 194K 是四个满分模型中最低的 token，它排第 4 只因 extension 1/2（丢了一个扩展检查）**——排序键在 token 之前先比 extension。若那一项通过，按 token tiebreak（194K < luna 306K）短 A 冠军会是 kimi。也就是说 kimi 的"无计划基线"既便宜又强，它的高成本形象完全来自 B 条件（+609K 计划税，与 qwen/luna 同类）。

短板照旧：14 次自测零缺陷发现（全场验证冗余之最）；`dependency_layers` 未显式层内排序（确定性靠实现细节）；长任务 5/10 与顶部有实距。定位：**任务形态未知时的默认选择**——它不在任何轴上是第一，但也从不掉出前列，这种"最小遗憾"属性在选型里非常值钱。

### glm-5.2 —— 短任务工程质量天花板 + 全场最便宜的"修复回路"

数据面：短 A #2（426K）/短 B #3（625K），跨条件最稳（源总表明示）；长任务 pass-1 只有 3/10，F3 定向反馈后 5/10（只改 `delivery_spool/__init__.py`，修订轮 513,512 token）。Reviewer #7（cross_hashability 未过）。

两点我特别看重：一是它的短任务实现（`_NodeRegistry`、hash bucket + 线性回退、cross-path equality、`__slots__`）是可维护性意义上的最佳工程，与 qwen 并列；二是 **+51 万 token 换 +2 milestone 是全场最便宜的边际改进**——它对"定向缺陷反馈"的响应效率极高。这不能回填成自主能力（协议明确），但对实际使用是有价值的信号：glm-5.2 适合放在有代码评审/反馈回路的流程里，而不是放养跑长活。短 B 625K 其实是满分组第 4 低——原点评的"偏高"是排名换算错误，已修正。

## 第三梯队：条件型选手（选对场景就是第一）

### mimo-v2.5-pro —— 经济学冠军，两颗小钉子

B 条件 raw 15/16 + resource 2/2 + 算法正确（deque Kahn O(n+e)），只花 190,320 token（每 criterion 11,895，约为 qwen 的 22%）。它还是全场唯一"计划让它又提分又省钱"的模型（raw +1、token −55%）。两个失分点都真实但都小：capacity 未拒 float（一行检查）、用 `python -B -m pytest` 生成 `.pytest_cache` 触发 gate（一次命令选择；同模型长任务 gate PASS 证明不是系统性缺陷）。长任务 3/10 提醒我们：**便宜换不来推进力**——它的 2.0M token 是前 5 名最低，milestone 也是前 5 名最低档。定位：成本敏感、有 lint/命令白名单护栏的短任务量产场景，修好两颗钉子就是性价比首选；严格合规发布线上有偶发风险。

### mimo-v2.5 —— 计划执行冠军的 A/B 面

B 条件第 1（16/16、342K），phi_3 给它 +3；这是"强模型规划、弱模型执行"假设在本轮唯一的完整正面证据。但把镜头拉开：无计划时 13/16 且 extension 0/2（A 条件唯一零扩展），长任务 gate FAIL、raw 4/10、6.22M token（全场最贵长跑）。**它的能力像一台需要轨道的机车**——轨道（计划）铺好了跑得又快又省，没有轨道时既贵又出轨。用于"planner-executor"流水线的执行端合适，独立接活不合适。

### doubao-2.1-turbo —— 被单一名次低估最多的候选

短 B #2（603K）、Reviewer #4、维度评估无重大缺陷，A/B 都 15-16/16。长任务只有 2/10（0.30），是纯粹的"推进力不足"，不是算法或纪律问题。如果你的工作负载以中短任务为主，它是比名次更好的选择；本轮所有"2/10 组"成员里我只对它给出这个评价。

### doubao-2.0-pro —— 数据里最值得追问的一行

长任务 raw 4/10 只花了 **897,544 token**——qwen 拿 8/10 花 3.58M，luna 拿 6/10 花 3.08M，它拿 4/10 花 0.9M。按 raw milestone 单价算（约 22.4 万/枚）比所有 ranked 候选低一个档位；短 B 也是 15/16 · 276K 的省钱型。它被严格榜除名的原因是 6/7 指令合规（gate FAIL），Reviewer 还排 #5。**如果只允许我对一个候选说"修好纪律再跑一轮"，我选它**——它可能是被 gate 埋没的性价比冠军，也可能低 token 恰是"少做少错"的另一面（0.50 coverage 封顶），一轮补测就能分辨。

## 第四梯队：有明确缺陷或强条件依赖

### deepseek-v4-flash —— 计划可拉动，规模与收尾是通病

A 13/16（且 execution 未完整走完）→ B 16/16（+3，计划增益第二大），长任务 coverage 0.45 是 2/10 组最高。但 Reviewer 资源 1/2、补充 6/8（deep_50000 超时 + cross_hashability），B 条件 900K、25 次请求——大规模场景和执行收尾在三条轴上反复暴露。中量级可用，别给它超大输入。

### deepseek-v4-pro —— 成本失控的反面教材

功能覆盖其实不差（A 15/16、B 16/16、Reviewer 7/8），但 B 条件 1,407,484 token 全场最高、31 次请求（并列最多）、2 次返工，加上 O(n²) 注册让 20,000 节点资源测试超时（短 B 与 resource 1/2 直接相关）。同门 flash 的钱花在请求密度上，pro 的钱花在返工和低效算法上——后者更难通过流程修复。除非只做小规模功能点，否则不推荐。

### minimax-m3 —— 唯一的"正确性风险"标签

全场唯一被计划弄退步的模型（A 14/16 → B 12/16，−2），根因是真实的逻辑缺陷：Kahn 分层时静默丢节点，4/4 dependency criterion 全灭。Reviewer 7/8 说明同类调试在另一次运行能过，所以这是"偶发但致命"型风险——静默错误比崩溃更贵。A 条件 1.25M token 也偏贵。在有强测试护栏前不建议用于依赖图/调度类逻辑。

### LongCat-2.0 —— 能力中上，纪律最不稳，成本被 harness 放大

三次运行两次 gate 违规（长任务 6/7；Reviewer 因创建 `test_targeted.py` 触犯保护文件），但功能面不差：短 B 16/16、Reviewer 官方/资源全过、13 次自测还真的发现并修掉一个问题（全场唯一"验证有回报"的案例）。评它要剥掉 provider 因素：无 cache 使 838K input 全价计费，同样行为在有 cache 的 provider 上成本会大幅下降。结论：模型能力约在中上游，工程纪律和 harness 环境把它拖到了榜尾。

### doubao-2.0-code / step-3.7-flash —— 两种垫底

doubao-2.0-code：全维度弱（A 12/16 exec 未完整、长 raw 1/10、Reviewer 6/8 资源 1/2），计划能拉 +3 但上限就在 15/16。唯一定位是低要求批量小改。

step-3.7-flash 更有意思，它是**两副面孔的极端**：自主条件全场最差（A 12/16 倒数、长任务 raw 0/10 全场唯一零、连宽松榜都垫底）；但给了计划立刻变成 B 条件 16/16、326,756 token——**满分组最便宜的一次运行**（代价：res 1/2，O(n²) 缺陷靠低验证蒙混未爆）。把它理解成"没有自主性的廉价执行器"：规格写得足够死时性价比很高，任何需要它自己拿主意的场景都归零。

### composer-2.5 † —— 参考行

Cursor harness、token N/A、无长任务/Reviewer 数据。A 14/16 → B 16/16（+2）说明计划吸收能力不错，resource 两条件都 1/2。只作跨 harness 参照，不参与排序，本文不给定位。

## 五条跨模型结论（我的读法）

1. **短任务满分已经不稀缺，顶部区分度不在"对不对"**。B 条件 10 个模型 raw 16/16。真正拉开差距的是：长程推进（qwen 独一档）、成本结构（190K 与 1.41M 同分）、协议纪律（三起 gate 案例）。以后选型问题应从"谁最强"改成"谁在这个约束下最强"。
2. **phi_3 计划是均衡器兼税收**：弱模型受益（step +4、dsflash +3、mimo-v2.5 +3、doubao-code +3），强模型交税（luna +574K、kimi +609K、qwen +302K、glm +199K，raw 全部 +0），一个受害（minimax −2），一个双赢（mimo-pro +1 且 −229K）。给强模型硬塞计划是负优化——这是本轮对 agent 编排最有操作价值的发现。
3. **gate 一票否决应保留，但要配 raw 并列陈述**。三起案例（B12、subtest_9、subtest_13）里违规都真实存在，清零是对的；错的是把 strict 0 讲成"没写代码"。现有严格/宽松双榜结构已经是正确答案，叙述层照着讲即可。
4. **token 对账要三层拆开**：总量（计费）、单位（效率）、构成（provider 因素）。本轮最大的两个叙述错误（qwen"最贵"、kimi"cache 占比最高"）都源于把一层的结论安到另一层上。cache 占比 0%（LongCat）到 96.1%（qwen B06）的跨度足以颠倒任何"谁贵谁便宜"的结论。
5. **验证投入与代码质量在本轮几乎无关**：kimi 14 次自测、luna 14 次验证、qwen 7 次自测全部零缺陷发现；唯一有回报的是 LongCat（13 次里修掉 1 个）。顶部模型缺的不是写对的能力，是"知道什么时候该停"的元认知——这可能是下一代评测该单独立轴的维度。

## 与原点评（模型逐个评价.md）的差异

原文档的证据工作非常扎实（130+ 项事实核对通过），我的分歧集中在四处判断：

1. **qwen 不是"成本天花板"**（原文已按此修订）：短 B 第 5 贵、长任务单位成本前 5 名最低、cache 占 96%。我把它改评为"产出密度最高，总量偏贵"。
2. **kimi 的"无短板"要打个星号**：短 A 的 extension 1/2 让它以最低 token 屈居第 4——这既说明它比原文写的更省，也说明它并非零瑕疵；"差一项就是 A 榜第一"比"四维前 4"信息量更大。
3. **doubao-2.0-pro 值得单独提级**：原文把它归入 gate FAIL 组一笔带过；我认为 0.9M token 拿 raw 4/10 是全场最异常（最好）的一组长任务经济学数据，应优先复测。
4. **step-3.7-flash 不是简单"垫底"**：长任务确实归零，但 B 条件"满分组最便宜"使它在"死规格执行器"这个细分定位上有真实价值——垫底与可用并不矛盾，取决于你是否永远给它轨道。
