### 短任务 8 维度逐项证据（B06 正文）

**维度 1：指令遵循 -- 优秀**
- audit 全项通过（passed=true, reasons=[], external_workspace_write=false, protected_files_ok=true, signature_ok=true）
- 主动读取 `instruction_ack.json` 模板（events [34]）确保交付格式精确

- 仅修改 4 个 solution 文件 + ack，仅使用标准库（copy、math、collections.OrderedDict）

**维度 2：核心业务语义 -- 优秀**
16/16 criterion 全过，四模块核心逻辑正确，且设计有独到之处：

- **recursive_patch**：`_merge` 辅助函数 deepcopy 后原地修改（第 30-44 行）。注释解释 key 顺序保留逻辑（第 31-33 行）："assigning to an existing key preserves its position while genuinely new keys are appended"。替换值 deepcopy 注释（第 42-43 行）："replacement dict keeps patch's own order"
- **dependency_layers**：`intern` 函数含 **cross-path equality 检查**（第 33-36、42-44 行）--unhashable 节点会检查 hashable 索引，hashable 节点也会检查 unhashable 索引。注释（第 64 行）："order by first appearance, not adjacency accident"
- **ttl_set**：注释解释设计决策（第 31-33 行）："No heaps, tombstones, or history queues that could retain stale object references"。注释解释非单调 clock 处理（第 40-41 行）："scan every live entry instead of stopping at the first unexpired one"。注释解释重复 key 处理（第 49-51 行）："a plain assignment would keep the old key object"
- **duration**：**`_scan(text, check_range)` 参数化设计**（第 23、56-60 行）：parse 使用 `check_range=True`，normalize 使用 `check_range=False`。比其他模型的"scan 不检查 range"设计更精确--显式控制是否执行范围检查。`_UNIT_MILLIS` 使用下划线分隔符（`86_400_000`）提升可读性

B06 的代码质量在已评价模型中与 B14 并列最高。`check_range` 参数化设计是独有的--它精确表达了 parse 和 normalize 对范围检查的不同需求。cross-path equality 与 B14 等价。注释密度高且信息量大，解释"为什么"而非"做什么"。

B06 的注释质量在已评价模型中最高--不仅实现正确，还解释了为什么选择当前设计而非其他看似合理的替代方案。

**维度 8：Token 效率 -- 较差**
- 总 token：863,422（input 108 + output 33,799 + cache 829,515）
- 每 criterion 成本：53,964 tokens（B13 为 21,384，B06 高出 152%）
- 每严格任务成本：215,856 tokens
- 18 次 LLM 请求，9 次 Bash（7 次自定义测试）
- cache 占比：96.1%（829,515 / 863,422）--最高
- input token 仅 108--极低，几乎全部走 cache

B06 token 成本在 10 个满分模型中列第 5 高（B03 1.41M、B02 900K、B07 880K、B01 869K 更高）。特征极为特殊：input=108 说明几乎所有输入通过 cache 提供，cache token（829K）构成成本主体。高 cache 占比远超 B13（87.5%）、B08（81.3%）、B14（85.2%）、B04（89.9%），可能是 provider 端缓存策略差异，而非模型行为差异。7 次自定义测试与 B04（14 次）相比较少，但仍多于 B14（3 次）和 B08（4 次）。output 33,799 与 B14（33,376）几乎相同，高于 B08（10,671）和 B13（5,880）。

代码质量与 B14 并列最高（cross-path equality、`check_range` 参数化、`__slots__`、高质量注释），无返工，首次写入即正确。高 cache token 主要是 provider 缓存策略的结果，不完全由模型行为决定。如果排除 cache 成本（仅看 input+output = 33,907），B06 的实际推理成本极低。但在按总 token 计费的场景下，B06 仍属偏贵一档（满分组第 5 高）。

### 画像：质量天花板 + 总量偏贵（非成本天花板）

**qwen3.8-max 是"质量天花板 + 总量偏贵"型选手**。长任务 8/10 的断层领先，来自 cross-path equality、`check_range` 参数化这种别人没有的细节实现--代码质量与 B14（glm-5.2）并列最高。代价是 token 绝对总量偏高：短 B 863K 在满分组列第 5 高（B03 1.41M、B02 900K、B07 880K、B01 869K 更高），长任务 3.58M 列严格榜前 5 名第 3；但按每严格 milestone 计（446,954），它反而是严格榜前 5 名中单位成本最低的。

### 三个关键观察

**① 长任务断层第一，且是唯一"接近完整"的候选**
8/10 milestone 意味着两个项目只丢 2 个。对比第二名 luna 的 6/10、第三名 kimi 的 5/10，领先幅度大（2 个 milestone = 4 个 criterion）。在所有候选完整闭环项目数都是 0/2 的情况下，它是离"做完一个完整项目"最近的。

**② 短任务不是第一，但稳定满分**
短任务 A/B 都是 16/16 满分，但排名只第 3、5--token 不占优（A 条件 561K，4 个满分里最贵；B 条件 863K，10 个满分里第 5 贵）。它的特点不是"单次效率"，而是"能力天花板高且稳"。

**③ phi_3 计划对它零增益**
A（无计划）16/16 -> B（有计划）16/16，raw 没变，但 token 从 561K 涨到 863K（+302K）。计划没帮它提升完成度，只多花了 token。这和"phi_3 是弱模型助推器"的结论一致--它本来就强，计划帮不上。

### 被忽视的 token 构成

短任务 B 的 863K 中，input 仅 108，cache 829K（占 96.1%）。这意味着：
- **在 cache 友好的 provider 上，qwen 性价比极高**（实际推理成本 input+output = 33,907，全场最低之一）
- **在无 cache 的 provider 上，qwen 会贵得离谱**（对比 LongCat 的 provider 无 cache，838K input 全价计费）

高总 token 主要是 provider 缓存策略的产物，不完全由模型行为决定。但按总 token 计费时，它确实是最贵的。

### 短板

- **token 总量偏高，但单位效率最优**：长任务 3.58M（严格榜前 5 名里第 3），短任务 B 863K（满分组第 5 高）。每严格 milestone token 446,954，是 luna（513,348）的 87%--单位效率是严格榜前 5 名中最好的，贵在绝对总量。
- **过度验证**：18 次 LLM 请求、7 次自定义测试，但代码首次写入即正确，测试未发现缺陷--与 B12（6 次请求、1 次测试）形成鲜明对比。

### 与 B12（mimo-v2.5-pro）的性价比对照

这是评价 qwen 时最值得参照的对比（详见 `dimension-evaluations-spec-conformant-v2.md` 补充分析章节）：

| 指标 | qwen（B06） | mimo-v2.5-pro（B12） |
|---|---|---|
| 严格 criterion | 16/16 | 0（gate 清零） |
| raw criterion | 16/16 | 15/16 |
| resource | 2/2 | 2/2 |
| token | 863K | **190K（低 78%）** |
| 算法 | Kahn O(n+e) | deque-based Kahn O(n+e)（等价正确） |
| gate | PASS | FAIL（`.pytest_cache`） |

**B12 用 qwen 22% 的 token 达到其 94% 的 raw 完成度**，算法同样正确，resource 同样全过。唯一差别是 B12 用错了 pytest 命令 + capacity 没验证 int--都是"可修复的工程问题"，而非模型能力缺陷。如果工程流程能规避 `.pytest_cache`，B12 的性价比优势是模型固有的。

### 综合判断

qwen3.8-max 适合"需要持续推进、容忍中等 token 成本、看重代码质量与可维护性"的场景。如果任务长度是关键变量，它是首选；如果只看短任务效率，kimi/luna 更优；如果看重性价比且能控制工程流程，B12 修复后更优。

它的唯一遗憾是没人完整做出闭环项目（0/2），但它是最接近的那个。

### 短任务 8 维度评级（B07）

| 维度 | 评级 | 关键证据 |

| 指令遵循 | 优秀 | audit 全项通过，验证流程最完整（9+3 次测试） |

| **Token 效率** | **较差** | 880K（满分组第 3 高），22 次 LLM 请求（满分组前列，全场最多为 B03/B11 的 31 次），14 次有效验证 |

### 画像：防御性最强 + 泛化最强，但 token 最贵

**luna 是"防御性最强 + 泛化能力最强"型选手**。它的实现包含多项其他模型没有的独特边界处理：

- **`_nodes_equal` 异常安全等值比较**：处理 `__eq__` 可能抛异常的对象
- **`_deadline` 溢出处理**：`now + ttl` 溢出时返回 `math.inf`，唯一处理此边界的模型
- **`_decimal` 任意精度大数格式化**：使用 10^9 分块处理，是所有模型中唯一不依赖 Python int 自动转换的实现

这些在当前 criterion 集合下未被直接测试，但体现了对极端边界场景的深度考虑。泛化能力评级为全场最强。

### 三个关键观察

**① 短 A 第 1 + 长任务第 2，但短 B 掉到第 7--计划依赖反向**

这是 luna 最特殊的特性：
- 短任务 A（无计划）：16/16，306K tokens，**第 1**（4 个满分里 token 最低）
- 短任务 B（读 phi_3 计划）：16/16，880K tokens，**第 7**（10 个满分里 token 最高之一）

raw 没变（都 16/16），但 token 从 306K 暴涨到 880K（+574K），排名从第 1 掉到第 7。**luna 不依赖计划时反而更强，给了计划反而被带偏**--它可能花大量 token 去对齐计划细节，而这些细节它本不需要。

这个特性在真实部署里是双刃剑：
- 如果任务无现成计划，luna 是最优选择（短 A 第 1）
- 如果强制要求读计划，luna 的效率会显著下降

**② 长任务第 2，且是唯一能挑战 qwen 的候选**

长任务 6/10 milestone，仅次于 qwen 的 8/10。token 3.08M，比 qwen 的 3.58M 低 14%。每严格 milestone token 513,348，比 qwen 的 446,954 高 15%--单位效率略低于 qwen，但总量更低。

结合短 A 第 1 + 长任务第 2 + 维度评估中最强的防御性/泛化评级，luna 是综合表现最均衡的候选之一。它的短板是短 B（读计划后效率暴跌）。

**③ 原始轮 provider 403，靠补充重跑才拿到长任务数据**

luna 原始轮（subtest_7）因 provider 403 拦截未产出代码，两次尝试都在首个模型响应前失败。榜中的 subtest_7_rerun 是补充重跑结果（6/10）。这意味着 luna 的长任务数据只有一次有效运行，无法验证稳定性。

### 被忽视的过度防御

luna 的 22 次 LLM 请求在满分组中位居前列（B04 kimi 21 次、B06 qwen 18 次；全场最多是 B03/B11 的 31 次）。9 次自定义测试 + 3 次额外测试 + 2 次 smoke = 14 次有效验证操作，但这些测试**未发现任何缺陷**--代码首次写入即正确。

与 B12（6 次请求、1 次测试、190K token、15/16 raw）对比：luna 用 4.6 倍的 token 达到了多 1 个 criterion（16/16 vs 15/16）+ 更多防御性实现。额外的 token 主要投入在更密集的验证和更防御性的代码编写上。如果评价标准包含对极端边界场景的鲁棒性，luna 的额外成本有合理性；在当前 criterion 集合下，这些额外防御未被检测到。

### 短板

- **短 B 效率暴跌**：读计划后 token 从 306K 涨到 880K，排名从第 1 掉到第 7。这是 luna 独有的"计划反向依赖"特性。
- **token 成本高（短任务）**：短 B 880K（满分组第 3 高）；22 次 LLM 请求偏多（全场最多为 B03/B11 的 31 次）。长任务 3.08M 反而低于 qwen/kimi/glm 累计。
- **长任务只有一次有效运行**：原始轮 provider 403，无法验证稳定性。
- **过度防御**：`_decimal`、`_nodes_equal`、`_deadline` 等独特实现在当前 criterion 下未被测试，属于"为不可见的极端场景买单"。

### 综合判断

luna 适合"无现成计划、看重防御性与泛化能力、容忍高 token 成本"的场景。如果任务无计划，它是短任务最优（A 第 1）；如果任务长且复杂，它是长任务第二强（6/10）。但如果强制要求读计划，效率会显著下降。

- **长任务未挑战顶部**：5/10 milestone，落后 qwen（8/10）和 luna（6/10）。cache 占比高但总量也高。

### 综合判断

- `__slots__` 减少内存开销

但长任务原始轮 3/10、0.35 coverage，落后 qwen（8/10）、luna（6/10）、kimi（5/10）。短任务的架构优势没转化为长任务的完成度优势--长任务考验的是"持续推进两个项目"的能力，而非单模块的实现精致度。

**② F3 修订轮：从 3/10 到 5/10，但解读边界要划清**

glm5.2.fix 是 F3 反馈等级修订轮：
- **反馈内容**：被明确告知 `Spool.__init__` 需要兼容 `pathlib.Path` / `os.PathLike`
- **修订范围**：只改动 `src/delivery_spool/__init__.py`，加入 `os.PathLike` 到字符串路径的转换
- **效果**：严格 milestone 从 3/10 提升到 5/10（+2），coverage 从 0.35 提升到 0.55（+0.20）
- **token**：修订轮 513,512，累计 4,332,044（原始 3,818,532 + 修订 513,512）

修订提升了 2 个 milestone，但这是**定向缺陷反馈后的修复能力**，不能回填为 pass-1 自主能力。`repair-ranking-protocol.md` 明确规定：F3 修订产物不能与独立 pass-1 完全等价解释，不能覆盖原始轮记录。

**③ 最稳定的跨条件模型（短任务）**

短任务 A/B 都是 16/16 满分，且严格排名第 2、第 3--是 14 个模型里跨条件最稳定的（`overall-table-spec-conformant-v2.md` 明确指出）。phi_3 计划对它 raw 零增益（都 16/16），但 token 从 426K 涨到 625K（+199K），与 qwen/kimi 一样属于"计划帮不上的强模型"。

### 修订轮的 token 公平性处理

glm5.2.fix 排名中 token 为累计值（4,332,044 = 原始 3,818,532 + 修订 513,512），而非仅修订轮的 513,512。这是 `repair-ranking-protocol.md` 的规定：避免仅以少量修订 token 获得不公平优势。如果只算修订轮 513K，glm5.2.fix 的每严格 milestone token 会是 102,702（全场最低），但这会掩盖"它依赖原始轮 3.8M 的基础"。

按累计 token 计算，glm5.2.fix 每严格 milestone token 866,409，是 kimi（788,024）的 1.1 倍、luna（513,348）的 1.7 倍--修订后的效率仍低于原始就拿到 5/10 的 kimi 和 luna。

### 短板

- **长任务原始轮弱**：3/10 milestone、0.35 coverage，短任务的强没延续到长任务。
- **修订轮不等价 pass-1**：F3 反馈下的 5/10 不能等同于自主能力，排名中已标注。
- **短任务 token 中等**：B 条件 625K（10 个满分里第 4 低、第 7 高），单次大输出 25,511 token 是独有模式。
- **长任务 token 累计高**：4.33M（修订后），是严格榜前 5 名里最高的。

### 综合判断

glm-5.2 适合"短任务、看重实现质量与架构成熟度"的场景。它的 `_NodeRegistry` 和 cross-path equality 是短任务里最精致的实现，短任务 A/B 跨条件最稳。

但长任务是其短板：原始轮 3/10 明显落后顶部候选，修订轮 5/10 虽追平 kimi，但依赖 F3 反馈且累计 token 最高。如果任务以长任务为主，glm-5.2 不是首选；如果任务以短任务为主且看重代码可维护性，glm-5.2 是最强候选之一。

它的核心价值在于：**短任务实现质量天花板（`_NodeRegistry`），但长任务持续推进能力中等**--这印证了"短任务质量 ≠ 长任务能力"，与 qwen（短稳 + 长强）、luna（短强 + 长强但贵）形成三种不同的能力剖面。

- **capacity 类型验证缺失**：`ttl_strict_types` 失败，接受 float 作为 capacity。
- **长任务完成度中等**：3/10 milestone，落后顶部候选。长任务 token 1.99M 虽低，但每 milestone 效率仍弱于 qwen/luna。
- **短任务 A 偏弱**：14/16 raw（无计划时），排名第 10--无计划时能力中下。

### 综合判断

mimo-v2.5-pro 是评价方法论争议最大的候选。它的核心价值在于：

- **短任务性价比天花板**（190K token + 算法正确 + 15/16 raw），但被 gate 一票否决埋没
- **长任务稳定中等**（3/10、gate PASS、token 最低），但完成度不拔尖
- **计划增益显著**（phi_3 让 raw +1 且 token -55%），是弱模型助推器的典型

它适合"token 成本敏感、工程流程可控（能规避 `.pytest_cache`）、任务中等难度"的场景。如果工程流程能保证正确的验证命令，mimo-v2.5-pro 修复后是短任务性价比最优候选；长任务它能稳定 gate PASS 但完成度中等。

它的核心矛盾是：**能力不差（算法正确、raw 高），但工程纪律有偶发失误（`.pytest_cache`）**。这与 kimi（能力稳但验证过度）、luna（防御强但 token 贵）是不同类型的问题--mimo-v2.5-pro 的问题最易修复，但严格榜的 gate 机制不给修复机会。

### 全维度数据对照

| 候选 | 长任务严格榜 | 长任务 token | 短 A 严格 | 短 A raw | 短 B 严格 | 短 B raw | 维度评估关键缺陷 |

### 组内四象限分析

按"短任务能力 × 长任务完成度"分四象限（长任务都是 2/10，主要看短任务差异和缺陷性质）：

**① deepseek-v4-flash（#7）：短任务中等 + 长任务覆盖最高**
- 长任务 coverage 0.45 是本组最高（9/20 criterion 通过，比其他三个多 3 个）
- 短任务 A 13/16 偏弱（#11），但短任务 B 16/16 满分（phi_3 计划增益 +3）
- 维度评估（B02）：25 次 LLM 请求、900K token 均偏高（组内最高为 B03 的 31 次、1.41M），存在死代码（normalize 的 carrier 列表未使用）和 add 方法冗余扫描
- 短板：长任务 token 2.6M 但覆盖 0.45（效率中等）；短任务 A 无计划时偏弱

**② deepseek-v4-pro（#8）：短任务强 + 长任务 token 最贵 + 算法缺陷**
- 短任务 A 15/16、B 16/16，是本组短任务最强的
- 但长任务 token 2.79M，短任务 B 1.41M（10 个满分里最高）
- 维度评估（B03）：**O(n²) 注册缺陷**（hash 成功但不在 hash_map 时落入线性扫描），`res_dependency_20000` timeout；使用 list 替代 OrderedDict；31 次请求（与 B11 并列全场最多）+ 2 次 Edit 返工
- 短板：**token 效率与结果质量同时最差**--1.41M token 拿 16/16，且 resource 只过 1/2。这是"又贵又差"的典型

**③ doubao-2.1-turbo（#9）：短任务 B 第 2 + 长任务无重大缺陷**
- 短任务 B 16/16、603K token、第 2（仅次于 mimo-v2.5 的 342K）
- 长任务 2/10、0.30 cov，token 3.21M
- 维度评估（B08）：无重大缺陷，过度验证（4 次自定义测试含 weakref/gc，共 6 次 Bash），token 602K 比 B13（342K）高 76% 但结果相同
- 短板：长任务完成度低（2/10）但无明显算法缺陷；短任务过度验证导致 token 偏高

**④ minimax-m3（#10）：唯一短任务 B 退步 + 算法根本缺陷**
- 短任务 A 14/16 -> B 12/16（**phi_3 计划让它退步 -2**，是 14 个模型里唯一）
- 长任务 2/10、0.25 cov（本组最低）
- 维度评估（B11）：**dependency_layers 静默节点丢失 bug**--Kahn 算法中，当 current 层节点处理递减了 remaining 中后续节点 indegree 至 0 时，该节点既不进 current 也不进 next_remaining，被静默丢弃。导致 4/4 dependency criterion 全失败
- 短板：**核心业务语义不合格**（dependency_layers 模块失效），是本组唯一有根本性算法缺陷的

### 三个关键观察

**① 同样 2/10，缺陷性质完全不同**

- deepseek-v4-pro：算法 O(n²) 导致 resource timeout（性能缺陷，逻辑正确）
- minimax-m3：Kahn 算法静默节点丢失（逻辑缺陷，结果错误）
- deepseek-v4-flash：无重大算法缺陷，但长任务覆盖 0.45（最高）说明它做对了更多 criterion
- doubao-2.1-turbo：无重大缺陷，纯粹完成度低

**② phi_3 计划对这组影响分化**

| 候选 | A raw | B raw | 增益 |
|---|---|---|---|
| deepseek-v4-flash | 13/16 | 16/16 | **+3**（计划助推） |
| deepseek-v4-pro | 15/16 | 16/16 | +1 |
| doubao-2.1-turbo | 15/16 | 16/16 | +1 |
| minimax-m3 | 14/16 | 12/16 | **-2**（计划反向） |

minimax-m3 是唯一被计划带偏的--phi_3 计划让它从 14/16 退步到 12/16。这与 luna（短 A 第 1 -> 短 B 第 7）的"计划反向依赖"是同类现象，但 minimax-m3 的退步体现在 raw criterion 而非 token。

**③ deepseek-v4-pro 是"又贵又差"的典型**

1.41M token（短 B 最高）+ 2.79M token（长任务）+ O(n²) 算法缺陷 + 31 次请求 + 2 次 Edit 返工。它是所有模型中 token 效率与结果质量同时最差的案例--短 B 最高成本 + resource 仅 1/2。与 B12（190K token + 算法正确 + 15/16）形成最极端的性价比反差。

### 综合判断

这四个候选都是"长任务 gate PASS 但完成度低（2/10）"的中下水平选手。组内排序的合理依据：

1. **deepseek-v4-flash**（#7）：长任务覆盖最高（0.45），无根本缺陷，短任务 B 满分--本组最稳
2. **doubao-2.1-turbo**（#9）：短任务 B 第 2，无重大缺陷，长任务纯粹完成度低--本组短任务最强
3. **deepseek-v4-pro**（#8）：短任务强但 token 极贵 + 算法 O(n²) timeout--性价比最差
4. **minimax-m3**（#10）：唯一短任务 B 退步 + dependency_layers 逻辑缺陷--根本能力问题

它们共同的特征是：**长任务能通过 gate（指令合规），但无法持续推进项目（2/10 milestone）**。与顶部候选（qwen 8/10、luna 6/10）的差距不是"指令遵循"问题，而是"复杂业务持续推进能力"不足。

## 总结：15 个候选的能力剖面图谱

按"短任务能力 × 长任务能力 × token 效率"三轴，15 个候选可分为五类：

| 类型 | 候选 | 特征 |
|---|---|---|
| **全能顶部** | qwen、luna | 短任务满分 + 长任务 6-8/10，但 token 贵 |
| **无短板稳型** | kimi、glm-5.2 | 短任务满分 + 长任务 5/10，四维均衡 |
| **性价比黑马** | mimo-v2.5-pro | 短任务 raw 高 + token 最低，但 gate 偶发失误 |
| **中下完成度** | deepseek-flash/pro、doubao-2.1、minimax、doubao-2.0-pro、mimo-v2.5、LongCat | 长任务 2-4/10，各有缺陷 |
| **垫底** | doubao-2.0-code、step-3.7-flash | 长任务 0-1/10，全维度弱 |

**核心结论**：

1. **没有全能王**：qwen 长任务最强但总 token 偏贵（单位效率反而最优），luna 防御最强但短 B 暴跌，kimi 最稳但验证过度，mimo-pro 性价比最高但 gate 翻车。
2. **短任务 ≠ 长任务**：mimo-v2.5 短 B 第 1 但长任务 gate FAIL；qwen 短 A 第 3 但长任务第 1。
3. **gate 一票否决制有盲区**：mimo-v2.5-pro（短）、doubao-2.0-pro/mimo-v2.5（长）的 raw 完成度被 gate 掩盖。
4. **phi_3 计划是弱模型助推器**：step-3.7-flash +4、deepseek-flash +3、mimo-v2.5 +3，但对强模型零增益甚至反向（minimax -2、luna 排名暴跌）。
5. **token 效率与代码质量可分离**：mimo-v2.5-pro 用 190K 达到 15/16 + 算法正确，qwen 用 863K 达到 16/16 + 质量天花板--4.5 倍 token 换 1 个 criterion + 更强注释。
